# BuildLog MVP 개발 계획

> 2026-10-26 업데이트: 백엔드를 Django에서 **FastAPI**로, 프론트엔드를 Django 템플릿에서 **React**로 바꾸고, 데이터베이스를 개발·테스트용 **SQLite**와 운영용 **Supabase(PostgreSQL)**로 나누기로 결정해 전체 내용을 다시 작성했습니다. Phase의 목표와 순서, 완료 조건은 그대로 유지했습니다.

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버(FastAPI)에서도 로그인 상태와 작성자 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 서버 코드는 SQLite와 Supabase(PostgreSQL)를 같은 모델·API 코드로 다루도록 만듭니다. 개발·테스트 중에는 SQLite만 사용하고, Supabase 연결은 Phase 13에서 확인합니다.
- 실제 SQLite 데이터 파일, `.env`, `backend/.venv`, `frontend/node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- FastAPI, SQLAlchemy, React의 기본 기능을 우선 사용하고 꼭 필요하지 않은 외부 패키지는 추가하지 않습니다.

## 3. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/                 # FastAPI 서버
│  ├─ app/
│  │  ├─ main.py            # FastAPI 앱 생성, 라우터 연결, CORS 설정
│  │  ├─ config.py          # .env 환경변수 읽기
│  │  ├─ database.py        # SQLAlchemy 엔진·세션 (SQLite/Supabase 겸용)
│  │  ├─ models/            # SQLAlchemy 모델 (User, Study, Todo, ErrorLog, Comment, Like, Report)
│  │  ├─ schemas/            # Pydantic 요청·응답 형식
│  │  ├─ auth/               # 비밀번호 해시, JWT 발급·검증
│  │  ├─ routers/             # accounts, studies, todos, errors, public, comments, likes, reports
│  │  └─ tests/              # pytest 테스트
│  ├─ alembic/               # 데이터 구조 변경(마이그레이션) 기록
│  └─ requirements.txt
├─ frontend/                # React 서버
│  ├─ src/
│  │  ├─ pages/              # 회원가입, 로그인, 홈, 공부 기록, 할 일, 오류 기록, 공개 기록, 설정
│  │  ├─ components/         # 메뉴, 카드, 폼 등 공통 화면 조각
│  │  ├─ api/                 # 백엔드 API 호출 함수
│  │  └─ main.tsx
│  └─ package.json
├─ database/
│  └─ buildlog.sqlite3       # 개발·테스트용 실제 데이터 파일, Git 제외
└─ docs/                    # 요구사항, 동작 설명서, 개발 문서
```

운영 환경의 Supabase(PostgreSQL)는 이 저장소 폴더에 데이터 파일을 두지 않고, 연결 주소(`DATABASE_URL`)만 환경 변수로 연결합니다.

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 백엔드(Python/FastAPI)와 프론트엔드(Node.js/React)의 서로 호환되는 안정 버전을 확인합니다.
4. SQLite가 Python 환경에서 사용 가능한지 확인합니다.
5. 개발 서버 주소(백엔드·프론트엔드), 데이터베이스 파일 위치, 환경 변수 이름을 정리합니다.
6. 테스트 명령과 서버 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python·Node.js 실행 여부와 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

> 이 Phase는 이미 완료했습니다. 결과는 [setup.md](./setup.md)에 있습니다. (Python 3.14.6, FastAPI 0.162.0, React 19.3.1, SQLite 내장 확인 완료)

### Phase 1. FastAPI 백엔드 + React 프론트엔드 뼈대 만들기

#### 목표

기능 없이도 FastAPI 개발 서버와 React 개발 서버가 각각 실행되고, 화면에서 서버와 정상 연결되었는지 확인할 수 있게 합니다.

#### 작업

1. `backend/.venv`에 Python 3.14 가상환경을 준비합니다.
2. FastAPI, Uvicorn, SQLAlchemy, Alembic, python-dotenv만 먼저 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다.
3. `backend/app` 기본 구조(`main.py`, `config.py`, `database.py`)를 만듭니다.
4. 프론트엔드 주소만 API를 호출할 수 있도록 CORS를 설정합니다.
5. SQLite 파일 경로를 `database/buildlog.sqlite3`로 설정합니다.
6. 비밀값은 환경 변수에서 읽도록 하고 `.env.example`에는 항목 이름만 기록합니다.
7. SQLite 파일, 가상환경, `node_modules`, 개발 중 생성되는 파일을 `.gitignore`에 보완합니다.
8. 서버 상태를 확인할 수 있는 `GET /health` API 하나만 연결합니다.
9. Vite로 React 프로젝트를 만들고 `frontend/src` 기본 구조를 준비합니다.
10. React 홈 화면에서 `/health`를 호출해 "서버 연결됨" 같은 상태를 보여줍니다.
11. 이 Phase에서는 아직 데이터베이스 마이그레이션을 실행하지 않습니다. 사용자 모델을 먼저 만들어야 하기 때문입니다.

#### 예상 변경 파일

- `backend/app/main.py`
- `backend/app/config.py`
- `backend/app/database.py`
- `backend/requirements.txt`
- `frontend/package.json`
- `frontend/src/main.tsx`
- `frontend/src/App.tsx`
- `frontend/src/pages/Home.tsx`
- `.env.example`
- `.gitignore`

#### 확인 방법

- 백엔드 개발 서버가 오류 없이 시작되고 `/health`가 정상 응답하는지 확인합니다.
- 프론트엔드 개발 서버가 시작되고 브라우저에서 서버 연결 상태가 보이는지 확인합니다.
- 비밀 설정값, SQLite 파일, 가상환경, `node_modules`가 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 백엔드·프론트엔드 서버가 각각 정상 실행되고 서로 통신해야 합니다.
- 사용자 모델을 만들기 전에는 마이그레이션을 실행하지 않습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. `backend/app/models/user.py`에 SQLAlchemy 사용자 모델을 만듭니다.
2. 이메일은 필수이며 중복되지 않게 합니다. (데이터베이스 고유 제약)
3. 닉네임은 필수이며 중복되지 않게 합니다. (데이터베이스 고유 제약)
4. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용하도록 Pydantic 스키마에서 검사합니다.
5. 비밀번호는 passlib(bcrypt)으로 해시해서 저장합니다.
6. 로그인 식별값을 이메일로 설정합니다.
7. Alembic을 설정하고 사용자 모델의 첫 마이그레이션(revision)을 만듭니다.
8. 빈 SQLite 데이터베이스(`database/buildlog.sqlite3`)에 마이그레이션을 적용합니다.
9. pytest로 사용자 모델 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/models/user.py`
- `backend/app/database.py`
- `backend/alembic/env.py`
- `backend/alembic/versions/`
- `backend/app/tests/test_user_model.py`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.

#### 완료 조건

- 첫 마이그레이션과 사용자 모델 테스트가 모두 통과해야 합니다.
- 사용자 모델을 다시 바꾸기 위해 데이터베이스를 지워야 하는 문제가 없어야 합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입·로그인·닉네임 변경 요청·응답 형식을 Pydantic 스키마로 만듭니다.
2. `POST /api/accounts/signup`에서 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 회원가입 실패 시 서버는 실패 이유만 응답하고, 화면(React)에서 이메일과 닉네임 입력값은 유지하고 비밀번호 입력칸만 지웁니다.
4. 회원가입 성공 응답을 받으면 React가 로그인 화면으로 이동합니다.
5. `POST /api/accounts/login`에서 이메일·비밀번호를 확인하고 성공 시 JWT 토큰을 발급합니다.
6. 로그인 토큰은 httpOnly 쿠키로 저장해 화면의 자바스크립트가 직접 접근하지 못하게 합니다.
7. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
8. 로그인 성공 시 React가 내 기록 홈 화면으로 이동합니다.
9. 토큰이 없거나 올바르지 않은 요청은 API에서 401로 거부하고, React는 로그인하지 않은 사용자를 기록 화면에서 로그인 화면으로 돌려보냅니다.
10. `PATCH /api/accounts/me/nickname`으로 로그인한 사용자 자신의 닉네임만 바꿀 수 있게 합니다.
11. 공개 기록과 댓글에서 사용자의 현재 닉네임을 읽도록 준비합니다.

#### 예상 변경 파일

- `backend/app/schemas/accounts.py`
- `backend/app/routers/accounts.py`
- `backend/app/auth/password.py`
- `backend/app/auth/jwt.py`
- `backend/app/auth/dependencies.py`
- `backend/app/tests/test_accounts.py`
- `frontend/src/pages/Signup.tsx`
- `frontend/src/pages/Login.tsx`
- `frontend/src/pages/Settings.tsx`
- `frontend/src/api/accounts.ts`

#### 확인 방법

- `spec.md`의 회원가입, 로그인, 닉네임 경계값을 자동 테스트(pytest+httpx)로 확인합니다.
- 회원가입 성공 후 로그인 화면으로 이동하는지 확인합니다.
- 로그인 성공 후 내 기록 홈으로 이동하는지 확인합니다.
- 실패 시 유지하거나 지울 입력값이 정확한지 확인합니다.
- 로그인하지 않은 사용자가 기록 화면 주소로 직접 접근해도 볼 수 없는지 확인합니다.
- 다른 사용자의 닉네임을 바꿀 수 없는지 확인합니다.

#### 완료 조건

- 회원 관련 자동 테스트와 직접 화면 확인이 모두 통과해야 합니다.
- 이메일 확인과 비밀번호 찾기 기능은 만들지 않습니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

#### 목표

화면 작업 전에 세 가지 기록이 안전하게 저장될 공통 기반을 만듭니다.

#### 작업

4. 한 사용자가 같은 대상을 한 번만 신고하도록 데이터베이스 고유 제약을 둡니다.
5. 신고 성공·실패 응답을 만들고 React에서 안내를 보여줍니다.
6. 신고 실패 시 신고 이유를 유지합니다.
7. 신고만으로 대상 기록이나 댓글을 자동 삭제하지 않습니다.
8. 사용자 모델에 운영자 여부(`is_staff`) 항목을 추가합니다. 운영자 계정은 회원가입 화면이 아닌 별도의 초기 설정 방법(관리 스크립트)으로만 만듭니다.
9. `GET /api/admin/reports`는 `is_staff`인 사용자만 호출할 수 있도록 서버에서 검사합니다.
10. 일반 사용자는 신고 데이터를 조회하는 API를 호출할 수 없게 합니다.
11. 대상 기록이 비공개가 되어도 신고 기록은 운영자가 확인할 수 있게 유지합니다.
12. React에 운영자 전용 "신고 확인" 화면을 만들고, `is_staff`가 아닌 사용자는 접근할 수 없게 합니다.
13. 별도의 신고 처리 상태 기능은 만들지 않습니다.

#### 예상 변경 파일

- `backend/app/models/report.py`
- `backend/app/models/user.py` (운영자 여부 항목 추가)

- `backend/app/routers/reports.py`

- `backend/alembic/versions/`
- `frontend/src/pages/admin/Reports.tsx`
- 공개 기록·댓글 화면

#### 확인 방법

- 신고 이유의 0자·1자·500자·501자를 테스트합니다.
- 같은 사용자의 중복 신고가 차단되는지 확인합니다.
- 신고 후 대상이 자동 삭제되지 않는지 확인합니다.
- 일반 사용자와 운영자의 신고 접근 권한을 각각 확인합니다.

### Phase 12. 반응형 화면과 공통 실패 처리

#### 목표

모든 기능을 컴퓨터와 휴대폰에서 일관되게 사용할 수 있도록 화면과 안내를 정리합니다.

#### 작업

2. 메뉴, 버튼, 입력칸, 오류 안내의 모양과 위치를 통일합니다.

### Phase 13. 전체 통합 확인과 실행 문서 작성

#### 목표

처음 설치하는 사람도 실행할 수 있고, `spec.md`의 모든 기능이 함께 동작하는 상태로 마무리합니다.

#### 작업

1. 백엔드 전체 자동 테스트(`pytest`)를 한 번에 실행합니다.
2. 사용자 A, 사용자 B, 운영자 계정으로 권한 시나리오를 확인합니다.
3. 프로그램을 종료하고 다시 실행한 뒤 SQLite 데이터 유지 여부를 확인합니다.
4. 비공개 기록이 목록, 검색, 직접 조회 API에서 노출되지 않는지 다시 확인합니다.
5. `spec.md`의 기능별 확인 항목을 처음부터 끝까지 실행합니다.
6. `DATABASE_URL`을 Supabase(PostgreSQL) 연결 주소로 바꿔서 마이그레이션을 적용하고, SQLite와 동일하게 동작하는지 확인합니다.
7. 설치, 환경 변수, 데이터베이스(SQLite/Supabase) 준비, 백엔드·프론트엔드 서버 실행, 테스트 실행 방법을 문서로 작성합니다.
8. `.env.example`에 필요한 항목만 있고 비밀값이 없는지 확인합니다.
9. 실패한 항목만 수정하고 새 기능은 추가하지 않습니다.

## 6. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
